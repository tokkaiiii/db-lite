# 큰 셀 값은 서버에서 2KB로 잘라서 내려보낸다

**Status**: accepted

BLOB이나 XML 전체가 들어있는 컬럼을 조회하면 결과 그리드 렌더링이 눈에 띄게 느려졌다. 원인은 두 지점이 겹친 것: `server/internal/query/executor.go`는 행 개수만 `DefaultRowLimit`(1000행)으로 제한할 뿐 셀 값 크기는 그대로 두고, `client/src/pages/QueryPage.tsx`는 받은 값을 `String(cell)`로 변환해 가상 스크롤 없이 `<td>`에 그대로 꽂는다. 큰 값을 클라이언트에서만 자를지, 서버에서 자를지를 저울질했다.

서버에서 자르기로 했다 — payload 자체를 줄여야 네트워크 전송과 DOM 렌더링 부담을 동시에 없앨 수 있고, 클라이언트는 받은 걸 그대로 보여주기만 하면 되기 때문이다. 자르는 기준은 컬럼 타입(BLOB/XML 등)이 아니라 **최종 문자열 표현의 바이트 길이**로만 판단한다 — DB 드라이버마다 타입 메타데이터를 다루는 방식이 달라 타입 기준으로 가면 MySQL/Postgres/Oracle마다 별도 처리가 필요해지기 때문이다. 이 기준은 드라이버가 `[]byte`로 주는 값과 애초에 `string`으로 주는 값(예: Postgres의 TEXT/XML) 모두에 동일하게 적용된다. 임계값은 2,000바이트(2KB)로 고정 상수로 둔다 — 그리드는 결과를 훑어보는 용도이지 원본을 그대로 내려받는 용도가 아니라는 전제.

자른 사실은 `Result` 스키마를 바꾸지 않고, 잘린 문자열 끝에 `...(잘림, 원본 N바이트)` 마커를 이어붙이는 방식으로 알린다. 잘린 값의 전체 내용을 보는 기능(예: 셀 클릭 시 전체 값 조회)은 이번 결정 범위 밖이다 — 필요하면 쿼리를 좁혀서 재조회하는 것이 원칙이고, 실제로 필요성이 확인되면 그때 별도 ADR로 다룬다. 기존 `Result.Truncated`(행 개수가 `DefaultRowLimit`을 넘겨 잘렸는지를 나타내는 필드)와는 다른 개념이며, 이번 결정은 `Result`에 필드를 추가하지 않으므로 이름이 충돌하지 않는다.
