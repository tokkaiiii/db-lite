# 셀 다운로드를 JOIN 포함 임의의 SELECT로 확장하고, 이를 위해 정규식 대신 SQL 파서를 도입한다

**Status**: accepted (4방언 JOIN + 1단계 서브쿼리/파생 테이블 + 순수 `SELECT *` JOIN까지 구현 완료 — 아래 "구현 현황" 참고, CTE/UNION/혼합 와일드카드는 아직 후속 작업)

ADR 0009는 셀 다운로드(그리드에 표시된 잘린 값이 아니라 DB의 원본 바이트를 재조회)를 "PK가 있는 단일 테이블 `SELECT *`"로 좁혔다. 이유는 "이 셀 값이 정확히 어느 행에서 왔는지" 알아낼 방법이 좁은 정규식 파싱(ADR 0008) 밖에서는 없었기 때문이다. 사용자가 JOIN을 포함한 임의의 SELECT 결과에서도 셀 다운로드를 쓰고 싶어 해서, 이번에 그 범위를 넓힌다. **지원 범위**는 JOIN뿐 아니라 서브쿼리, CTE, UNION, 명시적 컬럼 목록까지 포함한 사실상 임의의 SELECT로 정한다.

이 범위를 지원하려면 "출력 컬럼이 어느 테이블의 어느 컬럼에서 왔는지"를 알아내야 하는데, JOIN·서브쿼리·UNION이 섞인 SQL에서 이를 정적으로 알아내려면 정규식으로는 불가능하고 **진짜 SQL 파서가 필요하다**. ADR 0008/0009는 "틀린 리라이트가 결과를 조용히 바꿀 수 있다"는 이유로 파서 대신 좁은 정규식을 택했다 — 이번 결정은 그 원칙을 뒤집는 것이다. 이 트레이드오프를 받아들이는 대신, 아래 안전장치(재조회값-그리드값 교차검증)로 "파서가 틀렸을 때 조용히 엉뚱한 값을 내려주는" 최악의 실패 모드를 막는다.

## 설계

- **DB별 파서**: DB Lite가 지원하는 MySQL/Postgres/MSSQL/Oracle 네 방언 모두 정식 지원한다. 방언마다 문법이 달라(TOP/LIMIT/ROWNUM, 인용 규칙 등) 각각 별도 파서 라이브러리가 필요하고(예: MySQL은 vitess/tidb 계열, Postgres는 pg_query_go 계열, MSSQL은 tsqlparser 계열, Oracle은 bytebase/omni 또는 plsql-parser 계열), 서로 다른 AST를 "alias → 테이블", "출력 컬럼 → 원본 테이블.컬럼"이라는 공통 매핑으로 정규화하는 계층을 하나 둔다.
- **PK 자동 주입**: 파서가 어떤 출력 컬럼의 원본 테이블을 알아냈어도, 그 테이블의 PK 컬럼이 SELECT 결과에 없으면 재조회로 행을 특정할 수 없다. ADR 0008이 LOB 컬럼을 서버에서 선제 처리하듯, 서버가 내부적으로 각 원본 테이블의 PK 컬럼을 `__pk_<alias>_<col>` 같은 이름으로 리라이트한 쿼리에 추가해 함께 조회한다. 이 컬럼들은 그리드에 노출하지 않고 재조회에만 쓴다.
- **서브쿼리/CTE**: 출력 컬럼이 파생 테이블(서브쿼리/CTE)에서 왔으면 그 안을 재귀적으로 따라가 실제 원본 테이블까지 추적한다. 도중에 집계나 컬럼 변형(예: `SUM(...)`, `a || b`)이 끼면 그 지점에서 원본 추적을 포기한다.
- **UNION**: 버치마다 같은 출력 컬럼 위치가 다른 테이블에서 올 수 있으므로, 행 단위로 "이 행이 어느 버치에서 왔는지"를 태깅해 버치별로 출처를 개별 추적한다.
- **추적 실패 시 컬럼 단위 fail-closed**: 파서가 특정 컬럼의 원본을 확신할 수 없으면(집계/연산식 결과, 윈도우 함수, 상관 서브쿼리, 파서가 모르는 문법 등) 쿼리 전체가 아니라 **그 컬럼만** 다운로드를 비활성화한다. 뷰(View)에서 온 컬럼은 별도 처리 없이, 기존 `PrimaryKeyColumns` 조회가 PK를 못 찾으면 자연히 비활성화된다.
- **오탐지 안전장치**: 다운로드 요청이 오면 파서가 추적한 table+PK로 재조회한 값을, 그리드에 이미 표시된 값(2000바이트로 잘려 있을 수 있으므로 같은 길이만큼 잘라서)과 문자열로 비교한다. 다르면 파서가 출처를 잘못 추적했거나 재조회 사이에 데이터가 바뀐 것이므로 500 에러로 다운로드를 거부하고 로그를 남긴다 — "비활성화되어야 할 다운로드가 조용히 엉뚱한 값을 내려주는" 실패를 막는 마지막 방어선이다.
- **API 스키마 변경**: `Result.Table string` / `Result.PrimaryKey []string`(결과 전체에 값 하나)로는 컬럼별·행별로 다른 출처를 표현할 수 없다. `ColumnOrigins []*ColumnOrigin`(컬럼마다 Table+PrimaryKey, 추적 불가 시 nil)과 행별 버치 태그로 교체한다. 프론트엔드의 `canDownloadCell`/`downloadCell`도 결과 전체 단위가 아니라 셀 단위로 다운로드 가능 여부를 판단하도록 다시 작성한다.

**범위 밖**: 디비버 스타일 인앱 값 뷰어는 ADR 0009와 마찬가지로 범위 밖이다. 파서 라이브러리 선정과 방언별 정규화 계층의 구체적 구현은 이 ADR이 아니라 별도 구현 계획에서 다룬다.

## 구현 현황

실제 구현은 "일반 JOIN(파생 테이블 없는 `t1 [AS] a1 JOIN t2 [AS] a2 ON ...`)"부터 좁혀 시작했고, 방언은 MySQL → Postgres → MSSQL → Oracle 순서로 하나씩 붙여 각각 Docker 컨테이너로 실제 검증했다. 서브쿼리/CTE 재귀 추적과 UNION 버치 태깅은 아직 후속 작업(wayfinder 이슈)으로 남아 있다.

**방언별 파서**:
- MySQL — `github.com/xwb1989/sqlparser` (순수 Go, vitess 초기 포크)
- Postgres — `github.com/wasilibs/go-pgquery`(파싱/deparse) + `github.com/pganalyze/pg_query_go/v6`(AST 타입·노드 생성 헬퍼). go-pgquery는 실제 Postgres 파서를 WASM으로 컴파일해 cgo 없이 크로스컴파일 가능하게 만든 pg_query_go의 드롭인 대체품 — 리턴 타입이 pg_query_go와 동일한 protobuf라 헬퍼 함수를 그대로 재사용한다.
- MSSQL — `github.com/ha1tch/tsqlparser` (순수 Go, T-SQL 전용 recursive-descent 파서, `.String()`으로 재직렬화 가능)
- Oracle — `github.com/bytebase/plsql-parser`(ANTLR 생성 PL/SQL 문법) + `github.com/antlr4-go/antlr/v4`. 처음엔 `github.com/bytebase/omni`(더 높은 수준의 래퍼)를 시도했으나, 이걸 추가하자 `go mod tidy`가 MySQL/Postgres/MSSQL/Oracle 드라이버 자체 버전까지 줄줄이 끌어올렸다 — 이 기능과 무관한 위험한 부작용이라 되돌리고 더 가벼운 `plsql-parser`(ANTLR 문법만, 드라이버 의존성 없음)로 바꿨다.

**Oracle 파서의 리라이트 방식이 다른 세 방언과 다르다**: xwb1989/sqlparser·go-pgquery·tsqlparser는 모두 AST를 고치고 다시 SQL 문자열로 직렬화하는 `String()`/`Deparse()` 함수를 제공하지만, ANTLR로 생성된 plsql-parser에는 그런 역직렬화 기능이 없다. 대신 파싱된 `selected_list`의 마지막 토큰이 원본 문자열의 몇 번째 문자에서 끝나는지 찾아, 그 위치 바로 뒤에 숨은 PK 컬럼 텍스트를 직접 이어붙인다 — ADR 0008의 정규식 리라이트가 원래 하던 것과 같은 발상의 텍스트 스플라이싱을, 이번엔 정규식 대신 실제 파스 트리가 찾아준 위치를 기준으로 한 것. 이때 ANTLR Go 런타임의 토큰 위치는 **바이트가 아니라 룬(rune) 단위**라, 스플라이싱도 `[]rune`으로 변환해서 처리해야 한다(이 프로젝트는 한국어 사용자 대상이라 테이블/컬럼명에 비ASCII 문자가 실제로 나올 수 있음).

**Oracle은 대소문자 폴딩이 이미 알려진 제약**: ADR 0008 당시 이미 발견된 사실(`internal/dbconn/lob.go`의 주석 참고)로, Oracle은 따옴표 없는 식별자를 항상 대문자로 저장하고 `USER_TAB_COLUMNS`/PK 조회는 대소문자를 구분한다. 즉 쿼리를 `FROM users`(소문자)로 쓰면 실제 카탈로그의 `USERS`와 매치되지 않아 PK를 못 찾고 다운로드가 자연히 비활성화된다 — 새 버그가 아니라 기존 ADR 0008 rewrite와 동일한 fail-open 동작이 그대로 이어진 것이다. 이번 JOIN 경로도 같은 이유로 대문자로 쓴 쿼리(`FROM USERS U JOIN ORDERS O ...`)에서만 다운로드가 활성화되는 것을 Docker Oracle로 확인했다.

**GROUP BY/DISTINCT 가드**: 첫 MySQL 구현을 Docker MySQL로 검증하는 과정에서 예상 못 한 제약을 하나 발견했다 — PK 자동 주입(위 "PK 누락 시" 항목)이 **`GROUP BY`가 있는 쿼리를 깨뜨릴 수 있다**. MySQL의 `only_full_group_by` 모드가 GROUP BY에 없는 컬럼이 SELECT 목록에 추가되는 것을 거부해, 원래 잘 실행되던 쿼리가 에러로 바뀌었다. `DISTINCT`도 비슷하게 위험하다 — 숨겨진 PK 컬럼이 추가되면 어떤 행이 "distinct"로 취급되는지가 조용히 바뀔 수 있다(에러가 아니라 잘못된 결과). 그래서 4개 방언 모두, 파서 경로는 `GROUP BY`/`HAVING`/`DISTINCT`가 있는 문장은 통계를 손대지 않고 통째로 건너뛴다(그 쿼리에 대해서는 다운로드 기능 전체를 비활성화).

## 1단계 서브쿼리/파생 테이블 지원

JOIN 다음으로, FROM 절의 서브쿼리(파생 테이블) — `SELECT ... FROM (SELECT ... FROM t) d JOIN ...` 형태 — 를 1단계(더 이상 중첩되지 않는) 깊이까지 지원했다. CTE(`WITH ...`)는 이번엔 다루지 않는다: MySQL 파서(2018년 포크, MySQL 8.0의 WITH 지원 이전 버전)가 애초에 WITH 문법 자체를 못 읽어 자동으로 파싱 실패(=다운로드 비활성화)로 fail-closed 되고, 나머지 세 방언은 파서가 WITH를 지원하긴 하지만 CTE까지 마저 다루는 건 별도 후속 작업으로 남겼다.

**출처 추적**: 외부 쿼리의 `d.col` 같은 참조를 만나면, 파생 테이블 `d`의 SELECT 목록에서 `col`이라는 이름으로 노출된 항목을 찾아(명시적 별칭, 또는 별칭 없을 때 각 방언의 기본 출력 이름 규칙 — 컬럼 자신의 이름, Postgres/Oracle은 마지막 식별자 부분) 그 항목이 다시 "진짜 테이블.컬럼"을 가리키는 단순 참조인지 확인한다. 파생 테이블 자신의 FROM에 테이블이 하나뿐이면 컬럼이 비한정(`col`)이어도 모호하지 않다고 보되, 둘 이상이면 그 컬럼은 추적을 포기한다. 파생 테이블이 GROUP BY/DISTINCT/HAVING을 쓰거나 그 안에 또 다른 파생 테이블/UNION이 있으면 그 지점에서 멈춘다(1단계 한정 — Russian-doll 중첩까지 재귀하지 않음).

**PK 도달 가능성 문제**: 재조회하려는 PK 컬럼이 파생 테이블의 SELECT 목록에 원래 없으면, 외부 쿼리는 SQL 스코프 규칙상 그 컬럼에 손을 댈 수 없다(서브쿼리가 노출한 컬럼만 바깥에서 보임). 그래서 PK 자동 주입이 JOIN 때와 달리 **두 지점**에서 일어난다 — 파생 테이블 자신의 SELECT 목록에 PK 컬럼을 노출하는 숨은 컬럼을 하나 추가하고, 외부 SELECT 목록에는 그 파생 테이블 별칭을 통해 같은 숨은 이름을 그대로 통과시키는 패스스루 컬럼을 추가한다. Oracle은 AST를 다시 SQL로 직렬화하는 기능이 없어 원본 텍스트에 직접 스플라이싱하는데, 이 경우 스플라이싱 지점이 두 곳(파생 테이블 자신의 SELECT 목록 끝, 외부 SELECT 목록 끝)이 되므로, 모든 스플라이싱 지점을 원본 텍스트 기준으로 먼저 다 계산해두고 위치 오름차순으로 한 번에 이어붙이는 방식으로 구현했다(그렇지 않으면 한 스플라이싱이 다른 스플라이싱의 위치를 밀어내 어긋난다).

**검증 중 발견한 버그 두 개** (MySQL로 처음 구현하다가 발견, 나머지 세 방언에도 같은 교훈 적용):
1. `internal/dbconn/pk.go`의 PK 조회 쿼리가 제약조건 이름만으로 조인하고 있었는데, **MySQL은 모든 테이블의 PK 제약조건 이름을 항상 "PRIMARY"로 고정**해서, 스키마 안에 PK 있는 테이블이 둘 이상이면 그 조인이 테이블 이름 조건 없이 다른 테이블의 PK 컬럼까지 섞어서 반환했다(우연히 두 테이블 다 PK 컬럼명이 "id"라 지금까지 결과가 우연히 안 틀렸을 뿐). MySQL/MSSQL/Postgres/Oracle 네 쿼리 모두에 `TABLE_NAME` 조인 조건을 추가해 고쳤다 — ADR 0011 작업과 무관한, 기존부터 있던 버그였다.
2. 파생 테이블 자신의 FROM이 테이블 하나뿐이라 컬럼이 비한정으로 쓰인 경우(`SELECT id, name FROM users`)를 처음엔 "한정 안 됨 = 모호함"으로 잘못 처리해 추적에 실패했었다 — "FROM에 테이블 하나뿐이면 비한정 컬럼도 안전"이라는 규칙을 빠뜨린 것.

네 방언 모두 Docker(MySQL/Postgres/MSSQL/Oracle)로 `FROM (SELECT id, name FROM users) d JOIN orders o ...` 형태를 실제 실행해, 파생 테이블 쪽 컬럼과 직접 JOIN된 테이블 쪽 컬럼 둘 다 정확한 테이블/PK로 원본 값을 재조회하는 것을 확인했다.

## 배포 후 발견한 심각한 회귀: `SELECT * FROM a JOIN b`가 컬럼 1개로 잘림

실사용 중 사용자가 `SELECT * FROM CLIP_FORM cf JOIN CLIP_FORM_DATA cfd ON ...`(바로 이 JOIN 경로가 처음 도입되기 전까지 항상 잘 되던, `*`를 그대로 쓴 흔한 쿼리) 결과가 컬럼 하나(`PRODUCT_ID`)만 나오고 나머지가 전부 잘리는 현상을 보고했다 — 다운로드가 안 되는 정도가 아니라 **그리드 자체가 깨지는** 심각한 회귀였다.

원인: 4개 방언 파서 모두 `*`/`alias.*`를 "출처를 못 정하는 컬럼 하나"로 취급해 그 select-list 항목 하나만 건너뛰고(origin을 nil로 두고) 계속 진행했다. 그런데 `*`는 실제로는 **테이블의 실제 컬럼 개수만큼** 물리 컬럼으로 펼쳐지는데, 이 파서 경로는 스키마를 몰라 그 개수를 알 수 없다. 그 결과 `Result.Columns`를 자를 때 쓰는 `visibleCount`가 "파스 트리의 select-list 항목 개수"(와일드카드 하나면 1)로 계산되어, 실제 드라이버가 돌려준 수십 개 컬럼 중 **첫 번째 것만 남기고 나머지를 잘라버렸다**. (Oracle만 예외적으로 원래부터 안전했다 — Oracle 문법은 `selected_list: '*' | select_list_elements (...)`로 `*`를 아예 별도 최상위 대안으로 둬서, 이미 있던 "bare `SELECT *` 거부" 가드가 우연히 이 케이스도 막고 있었다.)

고쳤다: 4개 방언 모두, select 목록 어디든 와일드카드(`*` 또는 `alias.*`)가 하나라도 있으면 그 문장 전체를 **통째로 건너뛴다**(그 컬럼만 origin을 nil로 두는 게 아니라 `ok=false` 자체를 반환) — 개수를 신뢰할 수 없는 상황에서는 아예 손대지 않는 편이 안전하다는 원칙. 회귀 테스트(`joinorigin_wildcard_test.go`)로 4개 방언 모두 bare `*`와 `alias.*` 두 형태를 남겼고, 사용자가 보고한 것과 동일한 스키마 모양으로 Docker MSSQL에 재현해 수정 후 6개 컬럼이 모두 정상적으로 돌아오는 것을 확인했다.

## 순수 `SELECT *` JOIN도 다운로드 지원

위 회귀를 고치고 나니 자연스러운 다음 질문: 사용자가 실제로 원했던 건 "`SELECT *` + JOIN에서도 그리드가 안 깨지는 것"뿐 아니라 "거기서도 다운로드가 되는 것"이었다. 사전 조사(이 대화의 grilling 세션 참고)로 위험도를 따져본 결과, 아래 조건에서는 안전하게 지원 가능하다고 판단해 구현했다.

**왜 가능한가**: SQL 표준은 `*` 확장 순서를 명확히 정의한다 — `SELECT * FROM t1 JOIN t2`는 t1의 스키마 컬럼 순서 그대로, 이어서 t2의 스키마 컬럼 순서 그대로 나온다. MySQL/Postgres/MSSQL/Oracle 네 방언 모두 이 규칙을 따른다. 그래서 각 테이블의 컬럼 목록(ADR 0008이 이미 만든 `dbconn.LOBColumns`로 조회)만 알면, **쿼리 텍스트를 전혀 건드리지 않고도** 결과의 각 물리 컬럼이 어느 테이블에서 왔는지 위치만으로 계산할 수 있다. 컬럼 이름 매칭이 필요 없어서(서브쿼리 추적 때보다 오히려 더 단순함), 그리고 PK도 어차피 `SELECT *`가 전부 선택하니 이미 결과 안에 들어있어 숨은 컬럼 주입도 필요 없다 — `expandWildcardOrigins`(새 파일 `wildcard.go`, 4개 방언 공용)가 하는 일은 그냥 "각 테이블 스키마 컬럼 개수만큼 순서대로 나열하며 그중 PK 위치를 표시"뿐이다.

**범위는 1단계로 좁혔다**: 순수 `SELECT *`(select 목록 전체가 와일드카드 하나)만 지원하고, `t1.*, t2.col, t1.col2` 같은 혼합 목록은 여전히 다운로드를 통째로 비활성화한다(이전과 동일한 안전한 실패). 서브쿼리(파생 테이블) 안에 있는 테이블의 `*`도 지원하지 않는다 — FROM에 파생 테이블이 하나라도 섞여 있으면 이 경로를 타지 않고 그대로 비활성화된다.

**여전히 남은 안전장치**: 스키마 조회(`LOBColumns`)가 실패하거나 빈 목록을 반환하면 그 순간 전체 origin 추적을 포기한다(부분적으로만 포기할 수 없다 — 한 테이블의 컬럼 개수를 모르면 그 뒤 모든 테이블의 물리적 위치 계산이 틀어지므로). 그리고 기존에 이미 있던 재조회값-그리드값 교차검증이 여기도 그대로 적용된다 — 혹시라도 위치 계산이 어긋나도 조용히 틀린 값을 내려주지 않고 다운로드가 거부된다.

Docker(MySQL/Postgres/MSSQL/Oracle) 네 개 모두에서 `SELECT * FROM users u JOIN orders o ON ...`을 실제 실행해, 두 테이블의 컬럼이 스키마 순서대로 정확히 나열되고 양쪽 다운로드가 정확한 테이블/PK로 원본 값을 재조회하는 것을 확인했다.

이 사고가 남긴 교훈: 이번 JOIN 기능 검증 때 실제 DB로 직접 돌려본 쿼리들이 전부 명시적 컬럼 목록(`SELECT u.id AS uid, u.name, ...`)이었고, **정작 원래 지원 목표였던 `SELECT *` 형태의 JOIN 쿼리는 한 번도 실제로 실행해보지 않았다** — 검증 시나리오에 구멍이 있었다.
